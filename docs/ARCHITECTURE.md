# Nano Java architecture

Nano Java runs J2ME MIDlets (CLDC 1.1 / MIDP 2.0) on the Nintendo DS. It
has three layers:

```
 classlib/src   Java: java.lang, java.util, java.io, javax.microedition.*,
                com.nokia.mid.*, nanojava.* (glue)        -> classlib.jar
 src/           C99, portable: the VM (src/vm), ZIP/inflate/PNG (src/util),
                MIDP natives and the rasterizer (src/midp)
 platform/      one directory per target, implementing src/pal/pal.h:
                host (headless, for tests) and nds (libnds/calico)
```

Everything the C code needs from a machine is in `src/pal/pal.h`: time,
console output, input events, presenting a frame, a data directory and a
fatal error screen. Porting to a new target means implementing those
functions and a `main` that starts the VM.

## The VM (src/vm)

| File | Role |
|---|---|
| `vm.h` | All core types (`Object`, `Class`, `Method`, `Thread`, `Slot`...) and the internal API |
| `classfile.c` | Parses class files into unlinked `Class` structures |
| `class.c` | Loading, linking (field layout, vtables, native binding), lookups, subtype checks, `java.lang.Class` mirrors |
| `interp.c` | The interpreter, invocation, class initialization, exceptions |
| `thread.c` | Green threads, monitors, `wait`/`notify`, `sleep`, the scheduler |
| `heap.c` | Java heap and mark & sweep collector |
| `string.c` | `java.lang.String` helpers and the intern table |
| `natives_lang.c` | Natives of `java.lang` and `nanojava.*` |
| `resource.c` | Where classes and resources come from (class library, application jar) |
| `vm.c` | Start-up: core classes, the boot thread |

Key design points:

- **Values are `Slot`s** (a union of int, float and reference, pointer
  sized). `long`/`double` take two slots. Object fields, statics, locals
  and the operand stack all use slots.
- **No C recursion for Java calls.** Invoking a method pushes a `Frame` and
  the interpreter loop continues. The caller's `pc` stays on its invoke
  instruction while the callee runs, which keeps exception ranges exact;
  the callee's `ret_skip` says how far to advance on return.
- **Re-executable instructions.** Anything that has to wait (a class
  initializer, a contended monitor, `sleep`, `wait`, waiting for input)
  leaves `pc` unchanged and returns to the scheduler; the instruction runs
  again later. Natives do the same by returning `NATIVE_BLOCK`, keeping
  their progress in `Thread.native_phase`. `NATIVE_INVOKE` lets a native
  finish by calling a Java method (`Class.newInstance` runs the
  constructor this way).
- **Green threads.** One native thread; the scheduler runs each Java thread
  for a slice counted in backward branches and calls.
- **Garbage collection.** Non-moving mark & sweep over one arena with
  segregated free lists. Object fields are traced precisely (each class
  records its reference slots); thread stacks, statics and the C stack are
  scanned conservatively, made safe by a bitmap of object start
  addresses. `WeakReference` referents are cleared after marking.
- **Symbols.** Names and descriptors are interned, so lookups compare
  pointers.

## Class library (classlib/src)

Written in Java, compiled by javac with `-source 1.3 -target 1.3` against
itself, and packed into `classlib.jar` (linked into the DS binary). Natives
are kept to what Java cannot do: object identity, threads, I/O with the
platform, floating point formatting, and anything performance critical in
graphics.

- `nanojava.Boot` is the first Java code run: either a CLDC `main` (tests)
  or `nanojava.MIDletRunner`, which creates the MIDlet and runs the
  `Display` event loop on the boot thread.
- `javax.microedition.lcdui.Display` owns the screen back buffer, delivers
  input and paints. All application callbacks and painting are serialized
  with `Display.LOCK`.
- `LcduiBridge` and `MIDletBridge` are small public classes that give the
  `nanojava` package access to package-private lcdui/midlet internals.

## Graphics

Images are `short[]` pixels in the DS bitmap format (15-bit color, red in
the low bits, bit 15 set) plus an optional `byte[]` alpha plane, so a frame
can be copied to VRAM unchanged. `src/midp/gfx.c` draws all primitives,
blits with the 8 Sprite transforms and alpha blending; `font.c` draws the
built-in bitmap fonts generated by `tools/genfont.py` (DejaVu Sans).

## Sound

```
 Java (MMAPI)          nanojava.Audio natives        platform              synthesizer
 Player / Manager  ->  src/midp/natives_audio.c  ->  pal_audio_*  ->  src/audio/synth.c
                       src/audio/media.c                                 sound channels
                       (MIDI, WAV, tones -> events/PCM)
```

- `javax.microedition.media.PlayerImpl` keeps the MMAPI state machine,
  timing, looping and listener events in Java; the natives only decode,
  start, stop and set volumes.
- `src/audio/media.c` turns MIDI files into a flat list of channel events
  with absolute times in milliseconds (tempo map applied), MMAPI tone
  sequences into the same kind of list, and WAV into 16-bit mono PCM.
- `src/audio/synth.c` is a sequencer plus a synthesizer that does not mix
  samples: it plays notes on 16 DS-style hardware channels (looping 32
  sample waveforms with a pitch-dependent rate, PSG noise for drums, PCM
  for clips) and updates their volume and pitch for envelopes and MIDI
  controllers. General MIDI programs map to 16 families, each with a
  waveform (`src/audio/waves.h`, from `tools/genwaves.py`) and an ADSR
  envelope. It is integer-only.
- On the **DS** the synthesizer runs on the ARM7, in Nano Java's own ARM7
  program (`platform/nds/arm7`, calico's standard services plus a 250 Hz
  synthesizer thread). The ARM9 queues commands in a ring in main RAM
  (`src/audio/nja_shared.h`) whose address it sends once over PXI; event
  lists and PCM are flushed from the ARM9 cache and read directly by the
  ARM7 and the sound hardware. The VM pays almost nothing for music.
- On the **host** (`platform/host/audio_host.c`) the same synthesizer drives
  a software model of the DS channels mixed at 32768 Hz, which
  `--audio-out` records to a WAV file. The `audio` test MIDlet checks MIDI,
  WAV and tone playback this way.

## Nintendo DS layout

`platform/nds/source/`:

| File | Role |
|---|---|
| `main.c` | Start-up and the launcher / game loop (games can be switched without rebooting: `vm_shutdown()` frees the whole VM) |
| `launcher.c` | The game list (details and icons from each jar's manifest, read lazily) and the MIDlet chooser for suites |
| `draw.c` | Drawing helpers for the launcher and the touch UI (RAM buffer, 32-bit copies to VRAM) |
| `vm_start.c` | Creates, runs and shuts down the VM (kept apart from libnds code: calico's `Thread` type clashes with the VM's) |
| `pal_nds.c` | The platform interface: time, video layouts, button mapping, input queue |
| `ui.c` | The touch screen: phone keypad and the emulator menu |
| `audio_nds.c` | `pal_audio_*`: commands to the synthesizer on the ARM7 |
| `../arm7/source/main.c` | The ARM7 program: calico services plus the synthesizer thread |
| `settings.c` | Per-game settings in `<game>.ini` |

Video layouts:

- **Fit** (default): the canvas is copied 1:1 into a 256x256 bitmap on
  the top screen and the 2D engine's affine background scales it to
  256x192 at no CPU cost (slightly tall canvases like 176x208 are only
  squeezed vertically). Canvases bigger than 256x256 are scaled in
  software. The touch screen is all UI.
- **Span**: the two screens form a 256x384 area and the canvas is shown 1:1
  across them; the touch screen rows below the canvas get a compact keypad.
- **Touch**: like Fit, but on the touch screen's engine, so touch-driven
  games can be played; touches are mapped back through the scaling to
  canvas coordinates. The top screen shows an information panel (button
  map, soft key commands, FPS). While the menu is open the touch screen's
  scaling is switched off so the menu is drawn 1:1, and the game image is
  saved and restored around it.

The UI draws into RAM buffers (shared with the launcher, see `draw.h`) that
are copied to VRAM with 32-bit writes (VRAM ignores byte writes). While the emulator menu is open the VM is
simply not scheduled, and the VM clock (`pal_time_ms`) is paused so games
do not see a time jump.
